# Maintenance and Capability Decay

Use this reference for long-horizon, paused, or retention-sensitive plans. Maintenance protects a demonstrated capability; it is not a second full syllabus.

## Decay classes

| Capability | Typical risk | Maintenance signal |
|---|---|---|
| Durable concept or reasoning pattern | Retrieval weakening | Explain, derive, or solve a representative problem |
| Procedural skill | Fluency and setup weakening | Complete a bounded task without step-by-step help |
| Tool or framework implementation | Version drift and operational decay | Reproduce a small current task and verify against current sources |
| Integrated project capability | Context and judgment decay | Revisit an artifact, debug a variation, or make a trade-off |
| Safety or regulated practice | Authorization and procedure drift | Use current supervised or approved verification |

## Maintenance rule

After evidence is demonstrated, record a relative maintenance trigger such as after the next milestone, after a meaningful gap, before reuse, after a tool change, or when a transfer check fails. Choose the smallest retrieval or reuse task that can detect decay. Do not schedule maintenance during every active learning block unless the user requests that level of detail.

During a capacity shock, preserve high-leverage or safety-critical maintenance first, reduce optional reinforcement, and record what was deferred. When a capability fails maintenance, return to the smallest error-to-intervention loop rather than rebuilding the entire branch.
