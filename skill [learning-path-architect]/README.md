# Learning Path Architect

## What this skill is

`learning-path-architect` turns an unstructured learning request into a coherent, executable learning system. It is designed for situations where a simple list of topics is not enough because the learner needs prerequisites, ordering, parallel routes, time estimates, evidence, progress tracking, or periodic replanning.

The skill works backward from the learner’s desired capability or outcome. It preserves the learner’s explicit goals, deduplicates shared foundations, identifies real dependencies, separates goals from technologies, distinguishes durable capabilities from volatile tools, and exposes the smallest credible next step.

It is not a generic “give me study tips” tool. It is an architect for building and maintaining a learning path.

## Choose the lightest useful mode

| If you need... | Ask for... |
|---|---|
| Prerequisites and coverage | A learning map |
| Ordering and what to do first | A roadmap plus a current action card |
| A large set of goals | A portfolio architecture and active frontier |
| Many vast domains studied together | A scalable multi-domain portfolio index, domain registry, bridge matrix, integration studios, and active frontier |
| A single complete document | A giant syllabus with stable IDs and internal sections |
| A time estimate or deadline plan | A time plan with effort, sessions, cycles, calendar ranges, and critical path |
| Ongoing adaptation | A roadmap plus Lite, Standard, or Structured tracker |
| A plan revision | A revision diff preserving completed evidence and stable IDs |
| You are stuck or unsure what to skip | A proportional diagnostic and learner-state record |
| You keep failing a milestone | An error classification and smallest corrective intervention |
| You want to know how to study | An adaptive learning loop with retrieval, practice, feedback, and transfer |
| You want study resources | A gap-to-resource register with a follow-up evidence task |

Do not request or generate the full portfolio machinery for a narrow question unless it will change the learner’s next decision.

## When to use it

Use this skill when any of the following situations apply:

| Situation | What the skill produces |

| You have a vague learning goal | A structured learning map with prerequisites and outcomes |
| You have a very long wall of text containing many things you want to learn | A portfolio architecture with goal families, shared foundations, priorities, dependencies, and linked or staged parts |
| You need to know what to learn first | A dependency-aware roadmap and active frontier |
| You need a single complete syllabus | One authoritative, integrated syllabus |
| You want several goals at once | A portfolio roadmap that distinguishes primary, parallel, sequenced, deferred, optional, and unresolved goals |
| You want MBBS, iBCI, full-stack development, robotics, or similar vast domains together | Separate domain cores plus shared foundations, justified bridges, interference-aware concurrency, and bounded interdisciplinary projects |
| You want to study multiple subjects in parallel | A capacity-aware concurrency plan that checks cognitive load, switching cost, maintenance, prerequisites, and recovery reserve |
| You have a deadline or limited availability | A minimum viable path with explicit trade-offs and deferred scope |
| You want to know how long learning may take | Effort, session, cycle, and calendar estimates with low/typical/high ranges and uncertainty |
| You want to study over months, years, or an open-ended period | A long-horizon portfolio architecture plus a rolling active frontier |
| Your roadmap must change as you progress | A tracker-based recalibration and periodic replanning workflow |
| You want to preserve the roadmap across files, sessions, or systems | A workspace-aware single-document, linked-part, or structured package delivery plan |

## What the skill can do

### Build learning maps and syllabi

The skill can recursively break broad goals into focused objectives. It works backward from the desired outcome rather than simply reproducing a list of subjects. It distinguishes conceptual prerequisites from performance prerequisites and adds only the foundations that prevent a real gap.

It can produce either a compact map, a single large syllabus, a roadmap, or an integrated portfolio. It does not force every request into the same output shape.

### Handle very long and multi-goal requests

The skill can process a long “everything I want to learn” request by assigning stable IDs, separating actual goals from examples and background context, grouping related items into goal families, deduplicating shared foundations, and recording coverage so that named goals are not silently lost.

It can represent a five-year plan, a six-month plan, a ten-day sprint, or an open-ended learning portfolio without pretending that all horizons should be planned with the same level of calendar detail.

### Coordinate many vast domains together

For a portfolio such as **MBBS + iBCI + full-stack development + robotics**, the skill does not create one enormous flat checklist. It first builds a portfolio index containing a north-star intersection outcome, one registry entry per domain, shared foundations, each domain’s irreducible core, cross-domain relationships, bridge competencies, integration studios, route states, safety boundaries, and the current active frontier.

The skill preserves the differences between the domains. MBBS remains a medically structured and high-consequence learning family; iBCI remains an interdisciplinary neuroscience, signal, hardware, algorithm, human-factors, and ethics family; full-stack development remains a software systems family; and robotics remains a mechanics, electronics, embedded, control, perception, planning, and integration family. Shared programming, mathematics, research, writing, or systems-thinking nodes are reused only when they genuinely serve multiple families. They do not replace domain-specific foundations.

The skill also models **cross-domain interference**. It considers switching cost, setup burden, notation changes, feedback delay, safety load, maintenance, and integration leverage before recommending parallel study. A typical starting architecture is one primary deep family, one supporting or bridge family, and at most one low-load maintenance or exploration family, unless tracker evidence supports more.

Interdisciplinary projects are bounded integration studios rather than giant projects that pretend to validate every domain. A biosignal dashboard may integrate iBCI, full-stack development, and human factors, but it does not prove clinical competence, advanced robotics, or medical authorization. High-consequence and regulated boundaries remain explicit.

### Keep changing domains current

The skill does not treat a large portfolio as a document that is created once and abandoned. It can maintain a freshness control plane containing source and claim records, research cutoff, version and region context, source health, revalidation triggers, update runs, conflicts, and affected stable IDs. When one framework, paper, device, standard, regulation, research result, or evidence expectation changes, the skill updates the affected subgraph and interfaces instead of rebuilding unrelated foundations.

It distinguishes a new item from a required item. A new paper, tool, or practice may be recorded as optional, exploratory, a bridge candidate, or a revalidation task until its relevance to the learner’s north star, dependency graph, target context, and evidence standard is established. Every update report states what changed, what stayed unchanged, what was not researched, and what should be checked next.

### Work across AI harnesses and environments

The learning graph is host-independent. The same portfolio can use verified MCP resources, APIs, databases, Git, local files, hosted workspaces, offline archives, downloadable packages, or chat-only staged output. The skill preserves stable IDs, schemas, relative links, source ledgers, update history, progress, conflicts, and revision records while remapping only environment-specific paths or URIs.

In an online environment, it can research current sources when web access is actually available. In an offline environment, it can continue stable planning using dated cached evidence, but it marks volatile information as stale or offline-unverified and queues online revalidation. It never invents background monitoring, persistence, browsing, scheduling, subscriptions, databases, or connector access.

### Understand skill release and installation status

Updating the working folder, rebuilding a portable ZIP, registering a skill in the host application, and downloading a client copy are separate layers. A larger or smaller download is not sufficient evidence by itself because compression settings and excluded files can change package size. When an update appears stale, compare the release manifest and hashes for the authoritative workspace and portable package, then distinguish **workspace-only**, **package-built**, **registration-unverified**, **client-stale**, and **matched** states. The skill can prove the files and package available to the current harness, but it cannot invent access to a private registry or mobile cache.

When Manus supports the standard skill-creator flow, the reliable registration attempt is to deliver the active `SKILL.md` path so the host can detect `/home/ubuntu/skills/*/SKILL.md` and generate its Add/Update card. The ZIP remains useful for portability and offline transfer, but a ZIP download alone does not prove that the skill was added to My Skills. See [`references/release-and-sync.md`](references/release-and-sync.md), [`templates/release-manifest.schema.json`](templates/release-manifest.schema.json), and [`scripts/build_release_manifest.py`](scripts/build_release_manifest.py).

For cross-harness transfers, the skill performs a compatibility check before import, preserves stable IDs and evidence, previews conflicts, records schema migrations, flags broken links, and queues unsupported operations instead of claiming they completed. For generated-plan evaluation, it separates deterministic contract checks from qualitative judgment and never treats a high structural score as proof of learner mastery. See [`references/portability-migrations.md`](references/portability-migrations.md) and [`references/structured-output-evaluation.md`](references/structured-output-evaluation.md).

### Compare routes before changing the plan

When capacity, deadlines, domain count, target depth, access, priorities, or the north star changes, the skill can create a proposed scenario instead of immediately rewriting the authoritative plan. It identifies affected dependencies, newly blocked or unlocked branches, critical-path changes, evidence consequences, maintenance load, freshness impact, safety boundaries, and the smallest viable alternatives. It uses qualitative bands or learner-provided weights rather than pretending to predict exact mastery dates. Rejected or deferred routes remain available with reasons and reversal conditions.

### Keep a massive portfolio healthy and usable

The skill can audit graph integrity and goal closure: required goals must have capabilities, prerequisites, practice, evidence, target levels, maintenance/revalidation, and an explicit route state. It can identify dangling dependencies, duplicate shared foundations, decorative or overloaded bridges, stale active nodes, bottleneck concentration, update debt, insufficient evidence, unsustainable concurrency, and excessive learner-facing complexity. These are architecture signals, not judgments about the learner.

Complexity budgets preserve all requested goals in the authoritative index while limiting what appears in the immediate response. The learner receives the current slice, one primary action, necessary choices, and optional deeper layers. Targeted questions such as “What should I do today?”, “Why is this prerequisite here?”, “What changed?”, “What can I skip?”, and “What if I add robotics?” are answered from the relevant graph slice rather than by regenerating the whole portfolio.

### Model dependencies and parallel learning

The skill identifies hard prerequisites, soft prerequisites, alternatives, reinforcement loops, shared artifacts, conflicts, and genuinely parallel branches. It does not assume that two topics can be learned in parallel merely because they are conceptually unrelated. It also considers cognitive load, switching cost, maintenance work, minimum continuity, and recovery reserve.

The result can be one demanding primary branch plus a compatible maintenance or transfer branch instead of an unsustainable collection of simultaneous high-load subjects.

### Break time into usable levels

When time planning is requested, the skill separates:

- **Effort time:** focused work;
- **Session time:** effort plus setup, transitions, notes, and shutdown;
- **Cycle time:** sessions plus spacing, feedback, recovery, and review;
- **Calendar time:** real elapsed time under availability, dependencies, interruptions, and waits.

It can decompose a plan as:

```text
horizon → phase → cycle → milestone → learning unit → session → activity
```

It provides low/typical/high ranges, estimate basis, confidence, critical-path implications, spacing requirements, feedback waits, reserve assumptions, dominant uncertainty, and the next calibration point.

### Track progress and recalibrate capacity

The skill can compare the original plan with actual observations rather than treating the original estimate as permanently correct. It can examine planned versus observed effort, completion ratio, interruptions, recovery time, repeated blockers, branches actually sustained, switching cost, retention, transfer, and evidence quality.

It then identifies the smallest failing assumption. It may recommend remediation, narrowing, reduced concurrency, maintenance, deferral, replacement, splitting, or pausing instead of simply adding more hours or blaming motivation.

### Replan periodically

A review follows a defined sequence:

1. Collect progress, effort, evidence, blockers, interruptions, recovery, and context changes.
2. Check whether evidence meets the intended performance standard.
3. Calibrate capacity, cognitive load, switching cost, and concurrency.
4. Recompute dependencies, active frontier, maintenance, and volatile-tool revalidation.
5. Decide what happens to each goal family.
6. Explain what changed and why.
7. Commit a checkpointed revision when a persistent workspace supports safe updates.
8. Expose the next primary action, optional parallel action, evidence target, and next review trigger.

### Expose the next action

Long plans include a compact current-action card so the learner does not need to navigate the entire architecture. It identifies the primary action, optional compatible parallel action, session boundary, evidence to produce, blocker response, handoff, and review trigger.

### Track assumptions and evidence

Complex plans distinguish stated, observed, inferred, unknown, and verified assumptions. The skill can record what would change if an assumption is wrong and how it will be validated. Evidence is matched to the target context: recall, guided practice, independent performance, transfer, retention, or a real-world artifact.

### Diagnose and correct learning problems

When a learner is stuck, the skill does not automatically add more topics or assume a motivation problem. It classifies the smallest likely issue—concept, procedure, transfer, retrieval, environment, overload, evidence, route, or one-off shock—and chooses a bounded intervention with an expected improvement signal and recheck trigger. A short diagnostic can also show whether material is safe to skip.

### Use an adaptive learning loop

When the learner asks how to study, the skill can create a compact loop: retrieve or predict, target the gap, practice deliberately, inspect feedback, apply the capability in a varied context, record evidence, and decide whether to advance, reinforce, remediate, maintain, narrow, or re-diagnose. This loop is used when it changes the next action; it is not added to every topic map.

### Track capability states instead of topic completion

The skill can distinguish unfamiliar, exposed, guided, practiced, transferable, retained, maintained, stale, and contradicted states. Each state is tied to a context, support level, evidence date, confidence, and smallest gap. A completed lesson does not automatically unlock advanced work; the evidence must match the intended performance context.

### Test routes with bounded experiments

When two routes are plausible, the skill can propose a short pilot with one major change, a capacity cap, success evidence, a failure signal, a stop rule, and a reversal condition. It uses the result to continue, revise, stop, or revert without rewriting the entire portfolio. This turns uncertain route choices into low-risk learning experiments.

### Learn the learner’s capacity

The skill can maintain a personal capacity profile for reliable availability, usable hours, cognitive load, recovery reserve, setup overhead, interruptions, switching cost, and sustainable branch count. It updates one assumption at a time from robust observations across cycles and does not expand the plan merely because one cycle was unusually fast.

### Keep three synchronized views

Large plans now have a complete portfolio view, a current phase view, and a today view. These are compressed displays derived from one authoritative graph and stable IDs. The skill hides detail when necessary but never silently deletes requested scope.

### Operate the portfolio as one runtime

The skill can maintain one canonical portfolio revision linking goals, domains, capabilities, dependencies, evidence, observations, capacity, experiments, scenarios, freshness, decisions, policies, and safety boundaries. It derives practical signals such as evidence coverage, maintenance load, dependency bottlenecks, switching exposure, uncertainty concentration, freshness debt, and active-frontier readiness. When records are incomplete, it reports unknown instead of manufacturing precision.

It can propagate uncertainty through dependent branches, model decay differently for recall, mathematics, procedures, programming, volatile tools, safety-sensitive work, and project maintenance, and produce reversible repair proposals for dangling links, missing closure evidence, stale actions, unsupported parallelism, and view drift. It also supports learner-selected policies such as conservative versus aggressive progression, single-track versus bounded parallel study, theory-first versus project-first routes, and maximum switching limits.

Safety profiles can constrain self-study, simulation, supervision, authorization, data, and self-certification for medicine, human-subject research, robotics, cybersecurity, finance, aviation, laboratories, and regulated engineering. Technical findings are translated into plain-language answers such as “why this is first,” “what can wait,” and “what proves readiness.”

For portability, the runtime can generate non-destructive migration previews that preserve stable IDs and expose conflicts. For evaluation, it can compare structured output records between revisions, while clearly distinguishing structural improvement from actual learner outcomes.

### Choose resources by function

Resources are selected for a named function such as explanation, reference, worked example, practice environment, feedback, project scaffolding, or assessment. Each resource is tied to a gap and followed by an evidence task. The skill avoids dumping links or using more resources to hide an unclassified failure.

## How to use the tracker

The tracker is useful when you want the roadmap to learn from your real performance. Do not wait until the end of a large course or year-long plan. Record a short observation after each bounded cycle, such as a week, two weeks, a milestone, or two to five study cycles.

Start with the human-friendly template:

[Learning Observation Tracker](templates/learning-observation-tracker.md)

Copy it into the workspace where the roadmap is stored, or ask the skill to create a tracker for a particular plan. Fill in the plan identity once, then add one row per completed cycle.

Choose the lightest tracker that can support the decision. Use **Lite** when tracking burden is a risk and you only need planned versus actual effort, completion, the main blocker, evidence, and the next action. Use **Standard** when interruptions, recovery, concurrency, switching cost, or periodic replanning matter. Use **Structured** when the records must be validated, aggregated, stored in a database, or processed automatically. See [Tracker modes](references/tracker-modes.md).

### What to record after each cycle

| Field | What to write |
|---|---|
| Planned effort | The focused work you expected to need |
| Actual effort | The focused work you actually used |
| Planned units | The number of learning units you intended to complete |
| Completed units | The number you actually completed |
| Sessions planned/completed | Whether the planned schedule was realistic |
| Interruptions | Missed, shortened, or interrupted sessions |
| Recovery units | Time needed to return to reliable progress |
| Blockers | Blockers that prevented or slowed work |
| Repeated blocker | Whether the same blocker appeared again |
| Branches planned/sustained | How many parallel branches you planned and actually maintained |
| Switching cost | Time or cognitive effort lost moving between branches |
| Retention/transfer evidence | Whether the capability remained usable in a new or unfamiliar context |
| Evidence quality | Unknown, self-report, artifact, automated, mentor-confirmed, stale, or conflicted |
| Variance reason | Why the actual result differed from the estimate |

Record unknown values as `unknown`; do not silently enter zero. A zero means you observed none. Unknown means you did not measure it.

When a milestone fails, also record the error pattern and the smallest intervention tried. Preserve effective and ineffective interventions in the learner history, but do not record unsupported claims about motivation, intelligence, personality, or health.

### When to review

Use a relative trigger instead of inventing a calendar promise. Good starting triggers include “after two completed cycles,” “after the next milestone,” “after three attempts reveal the same blocker,” or “immediately after a major change in work or life capacity.” Also trigger an event review after a failed milestone, a capacity shock, a goal change, a dependency conflict, or a tool change that affects the route.

### How to perform the review

Open the tracker’s **Review record** and complete the five sections. First summarize what was planned and what actually happened. Next check the evidence in its performance context. Then calculate or estimate the effort ratio, completion ratio, interruption frequency, recovery time, blocker frequency, sustained branch ratio, switching cost, and evidence confidence. Recompute the active frontier and maintenance obligations. Finally record the smallest failing assumption, the decision, the next primary action, the next evidence target, and the next review trigger.

The available decisions are **continue**, **advance**, **remediate**, **maintain**, **narrow**, **defer**, **replace**, **retire**, **split**, and **pause**. Preserve completed evidence and historical observations when making a revision.

## Structured tracker and automatic summary

For machine-readable tracking, use:

[Observation tracker schema](templates/observation-tracker.schema.json)

The schema can be mapped to a JSON file, spreadsheet, database, project system, or connected workspace. The skill may use a connected adapter when one is actually available and verified. It will not invent database access, desktop access, persistence, or synchronization capabilities.

To generate a recalibration summary from a JSON tracker, run:

```bash
python3 scripts/recalibration_report.py path/to/observation-tracker.json
```

The report summarizes robust ratios and flags conditions such as:

- Actual effort consistently exceeding plan
- Low completion ratio
- Frequent interruptions
- Repeated blockers
- Unsustainable parallel branches
- Weak retention or transfer evidence

The report is a decision aid. It does not automatically rewrite the roadmap and it does not diagnose motivation, ability, or health.

## A simple operating loop

For a new learning goal, ask the skill to build the appropriate map or roadmap. If the request involves time, provide availability, preferred session length, target deadline if any, and the evidence standard you need. Follow the active frontier rather than trying to execute the entire long-horizon architecture at once.

After each review trigger, update the tracker. Ask the skill to analyze the observations, or run the recalibration utility if the tracker is structured. Apply the recommended route change, preserve the previous checkpoint, and continue from the newly exposed primary action.

A useful request looks like this:

> Build a roadmap for my goal. I can reliably study 7 hours per week in three sessions. Track planned versus actual effort, interruptions, recovery, blockers, parallel branches, and transfer evidence. Review the plan after every two cycles and recalibrate the next active frontier.

## What this skill does not promise

The skill does not guarantee mastery by a particular date. It does not convert topic count into hours, treat nominal availability as reliable capacity, or infer learning from speed alone. It does not replace an instructor, mentor, professional qualification, regulated authorization, or safety supervision.

Diagnostics and adaptive interventions are evidence-informed planning aids, not clinical assessments or perfect measurements of learning. A successful diagnostic supports only the capability and context it actually tests.

For current tools, frameworks, regulations, security practices, or other volatile information, the skill may need current research. For persistent synchronization, it can only use capabilities exposed by the running AI harness, connected MCP server, project connector, filesystem, or workspace. If no automated workspace exists, it can still create a complete artifact or staged plan, but it cannot honestly claim hands-off synchronization.

## Capability, assessment, and project-progression layer

The skill is capability-driven rather than topic-driven. It converts important goals into observable capability records with stable IDs, prerequisites, target context, proficiency levels, evidence requirements, safety boundaries, volatility, maintenance triggers, and route states. Its common progression runs from awareness and conceptual understanding through guided practice, independent performance, debugging/optimization, systems integration, production/research competence, and review/leadership.

The skill can generate proportional diagnostics, coding and debugging tasks, design reviews, failure-injection exercises, source audits, replication tasks, transfer challenges, capstone rubrics, remediation routes, and rechecks. It distinguishes exposure, guided, practiced, independent, transferable, retained, maintained, stale, contradicted, and unknown evidence. Tutorials, time spent, topic counts, self-report, and one polished artifact do not automatically prove independent capability.

Projects now use staged ladders: orientation, foundation, integration, advanced, enterprise/research, and capstone/contribution. Each project states its primary and supporting domains, prerequisites, target level, artifact, rubric, assumptions, safety boundary, limitations, and what it does not prove.

For large portfolios, the skill can compare minimum viable, research, production-engineering, enterprise, medical/clinical-foundation, project-first, and maximum-depth routes. It preserves deferred goals in the coverage ledger but normally exposes one primary next action, at most one feasible parallel action, one evidence task, and one review trigger. Portfolio-health audits identify dangling prerequisites, missing evidence, overloaded branches, stale claims, overlarge projects, missing safety boundaries, and unrealistic infrastructure assumptions, then propose reversible repairs rather than rewriting the learner's goals silently.

## The role of this skill in the complete personal system

Hosted LLM environments are useful for planning, research, revision, validation, and export, but many of them are temporary. Unless a host explicitly verifies persistent storage and scheduled execution, this skill must not be treated as a permanent database, an always-on agent, or a background scheduler. In that phase, keep a downloadable copy of the workspace and treat the host as an intelligent planning and updating workshop.

The long-term purpose is to guide the learner. `learning-path-architect` is the intelligent planning layer:

```text
learning-path-architect
= understands goals, dependencies, evidence, progress, and roadmap design
```

The permanent application will eventually combine that guidance layer with the learner's own local tools:

```text
learning-path-architect
+ local workspace
+ local database or structured files
+ Freeplane
+ Discoverer
+ scheduler
+ optional local LLM
+ backups
```

In this final arrangement, Freeplane is the visual map interface, the local workspace is the durable record, Discoverer keeps changing knowledge under review, the scheduler runs only when verified, an optional local LLM provides offline assistance, and backups protect the learner's history. The skill remains the guidance layer that helps decide what to learn, why it comes next, what evidence proves progress, and when the route should change.

## Hosted phase versus local phase

| Phase | What it is good for | What must not be assumed |
|---|---|---|
| Hosted LLM phase | Create roadmaps, research updates, generate Freeplane maps, review progress supplied to the session, and export a portable workspace | Permanent memory, automatic weekly Discoverer runs, continuous synchronization, or a local Freeplane connection |
| Local computer phase | Keep the workspace, maps, backups, progress, and optional database available over time; connect Freeplane and optional local AI | That every feature is automatically safe or reliable without backups and permission checks |

The package is deliberately designed so that work created in the hosted phase can be carried into the local phase instead of being discarded.


## Freeplane learning-workspace bridge

This package can be used with a local Freeplane workspace through the companion bridge in the repository that contains this skill. Freeplane remains the visual editor; the workspace records provide structured goals, capabilities, dependencies, evidence, progress, source metadata, and revision history.

### Hosted-first mode

In a hosted LLM environment, the skill can create and revise a portable workspace containing JSON records and Freeplane `.mm` maps. Export the complete workspace as a ZIP when moving between environments. Hosted mode does not provide live control of a Freeplane desktop application unless a local bridge is running and reachable; do not claim live synchronization from a static ZIP or chat session.

### Local mode

On the local Windows computer:

1. Install Python 3.10 or newer and Freeplane.
2. Clone or download the companion repository.
3. Run `setup.ps1` from PowerShell.
4. Place Freeplane `.mm` files in the workspace `maps` folder.
5. Run `start-sync.ps1` to watch saved map changes.
6. Start the authenticated localhost MCP bridge when an LLM client needs access.

The companion commands are:

```powershell
python -m freeplane_sync.cli init --workspace C:\LearningWorkspace
python -m freeplane_sync.cli import --workspace C:\LearningWorkspace
python -m freeplane_sync.cli export --workspace C:\LearningWorkspace
python -m freeplane_sync.cli undo --workspace C:\LearningWorkspace
python -m freeplane_sync.cli redo --workspace C:\LearningWorkspace
python -m freeplane_sync.watch --workspace C:\LearningWorkspace
python -m freeplane_sync.mcp_server --workspace C:\LearningWorkspace --token CHANGE-ME
```

### Synchronization model

The bridge compares stable node IDs and snapshots. It detects added, renamed, moved, deleted, and note-changed nodes where represented by the Freeplane XML adapter. It creates a checkpoint before external writes and records a conflict instead of silently overwriting when both the map and structured workspace changed from the same base revision.

Freeplane’s own in-session undo/redo remains owned by Freeplane. The bridge does not promise to recreate Freeplane’s native undo stack after an application restart. It separately keeps recoverable saved-state revisions and supports workspace-level undo/redo; the saved-state restore is checkpointed first.

### Adapter rules

Treat the workspace manifest and revision records as the adapter contract. Discover and record whether the current host supports reading, writing, checkpoints, versioning, conflict detection, link verification, and MCP mutations. If a capability is not verified, mark it unavailable rather than claiming that a change was saved.

Use relative links between maps, preserve stable IDs across revisions, validate cross-map targets, and keep model/API credentials out of the workspace and repository. For large or high-consequence changes, produce a diff and checkpoint before applying mutations.

### Current bridge limitations

The initial bridge is a small standard-library implementation intended to make the workflow installable and testable without coding knowledge. It provides an authenticated localhost JSON-RPC/MCP-style endpoint and basic Freeplane hierarchy/notes round-tripping. Complex visual styling, floating positions, connector styling, and full native MCP protocol compatibility require subsequent adapter work and must not be assumed from the basic bridge.
