# Effort Sizing and Primary-Source Guidance

Use this reference only when the user asks how large a task is, how to prioritize effort, or where to study from. Do not attach effort labels or resources to a plain decomposition request.

## Relative effort

Use effort bands instead of invented calendar schedules:

| Band | Approximate shape | Typical use |
|---|---|---|
| **XS** | Focused concept, short configuration, or small verification task | One narrow leaf or bounded exercise |
| **S** | Guided build, familiar bugfix, or compact practice loop | A small cluster of related leaves |
| **M** | Integrated mini-project, unfamiliar debugging task, or migration exercise | A milestone joining several branches |
| **L** | Multi-branch capstone, ambiguous system, or substantial transfer challenge | A major application or final demonstration |

These are relative planning labels, not promises. If the learner supplies an available time budget, use the bands to compare scope and identify trade-offs; do not convert them into arbitrary weeks without a defensible basis.

## Primary-source protocol

When the learner asks for resources, prefer canonical and maintained sources in this order:

1. Official documentation, specifications, standards, RFCs, manuals, or authoritative institutional material.
2. Primary research papers or original project documentation when the topic is research-driven.
3. A small number of reputable secondary explanations only when they improve accessibility or fill a pedagogical gap.

Attach a source to the capability it supports and note its freshness boundary when the source is version-sensitive. Do not dump links, imply that a source was checked when it was not, or treat a source list as a substitute for practice and evidence.
