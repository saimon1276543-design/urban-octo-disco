# Cross-Domain Interference and Bridge Design

Use this reference when many domains are studied together and the learner wants parallel progress or interdisciplinary projects.

## Interference dimensions

For each pair of active families, assess conceptual similarity, notation/tool switching, setup burden, feedback delay, emotional or safety load, maintenance burden, and shared artifact leverage. Similar-looking topics can still interfere when they use different conventions; unrelated topics can coexist when their sessions are short and setup is stable.

Classify each pair as low, moderate, or high interference and state the reason. Use the matrix to choose concurrency, session spacing, day grouping, or a temporary handoff.

## Bridge competency test

A bridge competency is justified only if it:

1. serves at least two named families;
2. changes a real dependency, project, or evidence route;
3. has its own observable outcome;
4. does not duplicate a domain core;
5. can be practiced without requiring the entire portfolio to be complete.

Examples include biosignal processing bridging iBCI and robotics, software data pipelines bridging iBCI and full stack, or human factors bridging medicine, interfaces, and robots.

Further durable bridges include:

- crawl → parse → clean → store → index → hybrid RAG → agent;
- Python orchestration → Rust/C++ performance components → Go services → database/search infrastructure;
- MCP server → agent-to-agent protocol → bounded multi-agent dispatcher → verified result;
- Linux/QEMU/KVM/Docker/Nginx → secure MCP or inference hosting;
- multi-terabyte data quality → embeddings/features → lexical/vector/graph indexes;
- OSINT acquisition → provenance/entity resolution → evidence graph → Graph RAG;
- iBCI/robotics telemetry → calibration/Kalman filtering → data quality → ML analysis; and
- full-stack/API/network/database foundations → enterprise agent application.

Each bridge must specify source domains, target outcome, prerequisites, a bounded integration artifact, evidence, authorization, and what it does not prove. Parallel execution is justified only when dependencies, rate limits, memory, switching cost, and verification support it.

## Integration studio

An integration studio is a bounded project with a primary domain, supporting domains, a bridge objective, explicit exclusions, safety boundary, and evidence rubric. Keep it small enough to reveal transfer. If it becomes a platform spanning every domain, split it into staged studios.

When an integration project fails, diagnose whether the issue is a domain prerequisite, bridge competency, interface contract, integration scope, environment, or evidence design. Do not respond by expanding every family simultaneously.
