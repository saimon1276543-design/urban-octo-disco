# Massive Multi-Domain Portfolio Architecture

Use this reference when the learner wants to study many large domains together, such as medicine, brain-computer interfaces, full-stack development, robotics, law, languages, mathematics, or multiple professions. Treat the request as a **portfolio of capability systems**, not as one syllabus with every topic placed in one order.

## Portfolio layers

1. **North star and role intersection:** define what the learner wants to become able to do at the intersection of the domains. Examples include clinical neurotechnology researcher, medical-robotics engineer, or full-stack builder for biomedical systems.
2. **Domain families:** create one family for each major domain and subfamilies for disciplines, not for every named topic.
3. **Shared foundations:** deduplicate mathematics, scientific reasoning, programming, communication, research methods, ethics, safety, and project workflow only when they genuinely recur.
4. **Domain cores:** preserve each domain’s own irreducible foundations. Do not pretend that a shared Python course replaces anatomy, physiology, circuits, control, clinical reasoning, or software architecture.
5. **Bridge competencies:** add only the interdisciplinary capabilities that connect two or more families, such as signal processing for iBCI and robotics, human factors for clinical systems, or full-stack interfaces for data collection.
6. **Integration studios:** use bounded projects to test whether knowledge transfers across domains. Integration is evidence, not a reason to erase domain depth.
7. **Maintenance and revalidation:** preserve durable capabilities while revalidating volatile tools, standards, devices, regulations, and platforms.
8. **Active frontier:** expose only the current phase, cycle, and next actions. The complete portfolio remains available through the index or staged parts.
9. **Freshness control plane:** maintain source/claim mappings, volatility, research cutoff, source health, revalidation queue, update runs, conflicts, and affected-node revisions so changing domains can evolve without rebuilding stable architecture.

## Domain decomposition rule

For every major domain, record its canonical subdisciplines, target level, entry diagnostic, required evidence, irreducible prerequisites, volatile components, safety or authorization boundary, and relationship to other families. Use domain names as containers, not as learning objectives. “MBBS” must become a structured medical education family; “iBCI” must distinguish neuroscience, neural signals, hardware, algorithms, human factors, and ethics; “full stack” must distinguish software foundations, backend, frontend, data, security, deployment, and product evidence; “robotics” must distinguish mechanics, electronics, embedded systems, control, perception, planning, and integration.

Do not assume equal depth across families. A portfolio can have one primary deep family, several supporting families, and exploratory families. State the target level per family and the consequences of uneven depth.

## Cross-domain relationship types

Use a relationship matrix with only decision-relevant edges:

- Shared foundation
- Hard prerequisite
- Soft prerequisite
- Bridge competency
- Parallel but interference-prone
- Parallel and low-interference
- Shared artifact
- Integration dependency
- Alternative route
- Potential conflict
- Independent

A relationship must explain what changes: ordering, resource choice, cognitive load, safety review, project design, or evidence. Do not create an edge merely because two domains sound related.

## Interference and concurrency

Parallel learning is not free. Estimate each family’s novelty, setup cost, context-switching cost, maintenance load, safety burden, feedback latency, and integration leverage. Permit concurrent families only when the combined load fits reliable capacity and the learner can preserve continuity. In a massive portfolio, prefer one primary deep family, one supporting or bridge family, and at most one low-load maintenance/exploration family unless observed data supports more.

When the learner wants maximum speed, show the trade-off between breadth, depth, switching overhead, and forgetting. Increase concurrency only one branch at a time after evidence shows the current portfolio is sustainable.

## Integration without dilution

Do not make every domain contribute to every project. Select integration studios that test a specific bridge competency and have a clear scope boundary. Example: a biosignal dashboard may integrate signal processing, backend, frontend, and human factors without pretending to validate clinical diagnosis, advanced robotics, or full medical competence.

For high-consequence domains, keep educational integration separate from clinical authorization, human-subjects approval, patient care, device certification, or permission to operate equipment. Use simulation, synthetic data, approved datasets, supervised practice, and current authoritative requirements where appropriate.

## Scaling and delivery

When the portfolio is too large for one response, create an authoritative index containing the north star, family registry, dependency/relationship matrix, shared-foundations registry, bridge registry, current frontier, coverage ledger, revision state, and links or anchors to family parts. Each family part must stand alone enough to be useful but defer shared material to the index by stable ID.

Use progressive disclosure: portfolio architecture first, then current family details, then current action cards. Never expose every leaf when the learner only needs to know what to do now.

## Updating the portfolio over time

For a current portfolio, run a drift scan before a broad rebuild. Research flagged or requested scopes, map changes to stable domain/bridge/node IDs, revalidate the affected subgraph and interfaces, preserve unchanged foundations and completed evidence, and create an update report. Track changes in tools, research, standards, regulations, curricula, evidence expectations, and learner context separately. A new topic remains optional or exploratory until its relevance and route impact are established.

If the host is offline, continue using dated cached evidence for stable planning, label volatile claims as offline-unverified or stale, and queue online revalidation. If the host is another AI harness, import the manifest, source ledger, update history, queue, schemas, revisions, conflicts, and stable IDs; remap only adapter-specific paths or URIs. Never claim background monitoring unless a verified subscription, schedule, connector, or persistent process exists.
