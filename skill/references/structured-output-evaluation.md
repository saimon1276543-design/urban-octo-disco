# Structured output evaluation

Use this reference when evaluating generated maps, roadmaps, portfolios, revisions, or query answers rather than merely checking that package files exist.

## Evaluation record

Capture the input case, output artifact or normalized record, rubric dimensions, evidence excerpts or field checks, blocking failures, uncertainty, evaluator version, and result. Distinguish deterministic structural checks from human or model judgment. Never present a scaffold or self-score as proof that a generated plan is good.

## Minimum dimensions

Evaluate request coverage, dependency validity, scope fit, level calibration, actionability, evidence quality, revision safety, freshness/uncertainty, complexity control, multi-domain integrity, decision provenance, goal-to-evidence closure, query efficiency, and safety/automation honesty when relevant. Score only what the output demonstrates; mark unavailable rather than inferring success.

## Structured checks

Where a JSON or Markdown output has a contract, validate required fields, stable IDs, referential integrity, route states, evidence links, current action boundaries, source/revision metadata, and safety states. Use deterministic checks for structure and a separate qualitative score for educational judgment. Store failures as small rule changes or new regression cases.

## Evaluation safety

Do not use the evaluator to claim mastery, intelligence, motivation, health, or guaranteed outcomes. A high structural score means the output followed the contract for the tested case; it does not prove that the learning content is complete or that the learner will succeed.
